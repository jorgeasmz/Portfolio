## The model that did not ship

The German Credit dataset comes with something most datasets lack: an explicit cost matrix.
Approving someone who then defaults costs five times what turning away a good customer does.

A Random Forest was the obvious first attempt, and it reached 0.735 accuracy. Assuming nobody
ever defaults reaches 0.700, so on paper it was earning its keep.

Priced with the cost matrix it scores 153. Rejecting every single applicant scores 140.

The model was worse than closing the lending desk, and the accuracy figure never hinted at it.

| Model | Accuracy | ROC-AUC | PR-AUC | Recall | Cost |
|---|---:|---:|---:|---:|---:|
| **Logistic Regression** | 0.750 | **0.806** | **0.633** | 0.800 | **98** |
| Random Forest | 0.735 | 0.788 | 0.615 | 0.583 | 153 |
| Majority class | 0.700 | 0.500 | 0.300 | 0.000 | 300 |

Logistic regression beat it in every column. Less surprising than it looks: 800 training rows of
mostly categorical data is not much for an ensemble to find structure in, and plenty for it to
memorise. The forest stays in the codebase as `build_forest()`, since a choice that cannot be
compared against anything is not really a choice.

## Where to draw the line

`predict()` cuts at 0.5. That is a default rather than a decision, and it assumes both mistakes
cost the same.

Sweeping the threshold against the cost curve puts the minimum at **0.45**, for a cost of 96.
Accuracy keeps climbing well past that point. The most accurate threshold in the sweep costs a
quarter more than the one the service uses.

## Explaining a decline

When the answer is no, the applicant is owed a reason, and in several jurisdictions the lender
is required to give one. Every response carries the contribution of each field:

```json
{
  "risk_class": 0,
  "probability": 0.081,
  "model_version": "4d17fdeb3b1d",
  "contributions": {
    "checkin_acc": 0.7749,
    "savings_acc": -0.6333,
    "credit_history": -0.6052
  }
}
```

Producing that took more care than it looks. SHAP runs on the matrix the model actually sees,
where a categorical field spreads across one column per level, so the raw output is 61 numbers
attached to labels like `checkin_acc_A11`. Folding them back onto the twenty fields on the form
is what makes them mean anything.

The mapping is built from the encoder's fitted categories rather than by parsing the generated
column names, because `cat__checkin_acc_A11` cannot be split on underscores when the column name
already contains one.

There is a second catch. SHAP subsamples its background by default, which would explain the same
application two different ways on two different days. For a decision that might be challenged
months later, that is unacceptable, so the masker is pinned to the full background instead. A
test asserts the additivity property directly, since a mistake in the aggregation would break it.

## Keeping the receipts

Every scoring is written to PostgreSQL with the application, the explanation, the threshold in
force and a content hash of the artifact that decided. Not a version number: two builds tagged
`v1.2` are not necessarily the same model, and an audit needs the file.

The log pages by seeking on the primary key rather than with `OFFSET`, which walks the rows it
skips and shifts entries under anyone reading while new decisions arrive.

Cost cannot be measured from the log alone. Knowing whether a decision turned out expensive means
knowing whether the applicant paid, so there is an endpoint for reporting that back:

```
POST /decisions/41/outcome   {"defaulted": true}
```

`GET /summary` prices those outcomes with the same cost matrix that chose the model, and covers
only the decisions that have one. It also returns the distribution of predicted probabilities,
which is how the threshold becomes visible against the portfolio it is cutting. Until an outcome
arrives, the service can report how many applicants it turned away but not whether it should have.

## Access

Scoring and reading the log both sit behind a shared key in an `X-API-Key` header, compared in
constant time. With no key configured the endpoints return 503 rather than opening up. A credit
service that starts scoring for anyone because an environment variable went missing is a worse
failure than one that stops.

A single key fits service-to-service access, which is what this is. Several consumers would need
per-client keys and rotation, and that is a different design rather than a larger version of this
one.

## Running in production

The API runs as a Docker container on Render, with PostgreSQL on Neon and the Streamlit client on
Streamlit Cloud. Migrations run at container start rather than at image build, because the
database does not exist yet when the image is built.

Both free tiers sleep when idle. A measured wake-up took 32 seconds, so the client waits 90 and
says what is happening instead of showing a connection error.

## Testing

68 tests, 96% coverage. The suite never touches the network or a real database: it fits the
pipeline on a small synthetic frame with the same schema and runs against a throwaway SQLite
file. CI additionally applies the migrations to a real PostgreSQL service, which is where a
dialect difference would otherwise turn up in production rather than in a pull request.
