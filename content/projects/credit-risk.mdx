## Dataset and cost structure

The German Credit dataset contains 1,000 applications described by 20 attributes, of which 30%
are labelled bad credit. It defines a cost matrix: a false negative, meaning an approved
applicant who defaults, costs five units; a false positive, meaning a rejected applicant who
would have repaid, costs one.

Expected cost under that matrix is the selection criterion used throughout the project. Two
constant policies bound it on the held-out set: approving every applicant costs 300, rejecting
every applicant costs 140.

## Model selection

Three estimators were evaluated on a stratified 80/20 split.

| Model | Accuracy | ROC-AUC | PR-AUC | Recall | Cost |
|---|---:|---:|---:|---:|---:|
| **Logistic Regression** | 0.750 | **0.806** | **0.633** | 0.800 | **98** |
| Random Forest | 0.735 | 0.788 | 0.615 | 0.583 | 153 |
| Majority class | 0.700 | 0.500 | 0.300 | 0.000 | 300 |

The Random Forest reaches 0.735 accuracy and an expected cost of 153, which exceeds the 140 of
the reject-all policy. Accuracy does not separate the two. Logistic regression attains a lower
expected cost and higher ranking quality under both ROC-AUC and PR-AUC on 800 training rows of
predominantly categorical features, and was selected. The forest remains available as
`build_forest()` so the comparison can be reproduced.

## Decision threshold

The default `predict()` classifies at a probability of 0.5, which corresponds to equal
misclassification costs. Sweeping the threshold against the cost curve locates the minimum at
**0.45**, with an expected cost of 96. Accuracy continues to increase above that value: the
highest-accuracy threshold in the sweep carries an expected cost 25% higher.

## Explanations

Each response reports the contribution of every input field to the log-odds of default.

```json
{
  "risk_class": 0,
  "probability": 0.081,
  "model_version": "4d17fdeb3b1d",
  "contributions": {
    "checkin_acc": 0.7749,
    "savings_acc": -0.6333,
    "credit_history": -0.6052
  }
}
```

Contributions are computed with SHAP over the transformed design matrix, which holds 61 columns
because each categorical field is one-hot encoded into one column per level. The values are then
summed by originating field to produce one contribution per input.

The column-to-field mapping is derived from the encoder's fitted `categories_` rather than by
parsing generated column names, since a name such as `cat__checkin_acc_A11` is not separable by
underscore when the field name itself contains one.

The SHAP masker is pinned to the full training background. The default behaviour subsamples it,
which yields different explanations for identical inputs across calls. A test asserts the
additivity property, base value plus contributions equal to the model log-odds, which fails if
the aggregation is incorrect.

## Decision log

Each scoring is persisted to PostgreSQL with the submitted application, the computed
contributions, the threshold in force and a SHA-256 content hash of the model artifact. The hash
identifies the file rather than a release label, so a stored decision maps to the exact
parameters that produced it.

The log is paginated by seeking on the primary key. Offset pagination scans the skipped rows and
shifts entries between requests when new decisions are inserted concurrently.

## Outcome feedback

Realised cost requires ground truth, which is not available at scoring time. An endpoint records
it once a loan resolves:

```
POST /decisions/41/outcome   {"defaulted": true}
```

`GET /summary` applies the cost matrix to the decisions that carry an outcome and reports over
that subset only. It also returns the distribution of predicted probabilities across ten buckets,
which positions the threshold relative to the scored portfolio.

## Access control

The scoring and log endpoints require a shared key supplied in an `X-API-Key` header and compared
with a constant-time function. When no key is configured the endpoints return 503 rather than
accepting unauthenticated requests. A single shared key covers service-to-service access; per
client keys, rotation and rate limiting would be required for multiple consumers.

## Deployment

The API runs as a Docker container on Render, PostgreSQL is hosted on Neon and the Streamlit
client on Streamlit Cloud. Alembic migrations execute at container start rather than at image
build, since the database is not reachable while the image is being built.

Both free tiers suspend on inactivity. A measured cold start returned the health check in 32
seconds, and the client timeout is set to 90 seconds.

## Testing

The suite contains 68 tests at 96% statement coverage of the application and model packages.
Tests fit the pipeline on a synthetic frame following the production schema and run against a
temporary SQLite database, so neither network access nor an external database is required. CI
additionally applies the migrations against a PostgreSQL service container to detect dialect
differences before deployment.
